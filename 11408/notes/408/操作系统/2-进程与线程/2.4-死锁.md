# 2.4 死锁

> [!abstract] 一句话总结
> 死锁是多进程因竞争不可剥夺资源形成的循环等待僵局，解决核心在于破坏四必要条件、动态避免进入不安全状态或检测后解除。

## 核心要点
### 考点1：死锁概念与产生条件
**死锁是多个进程因竞争资源陷入相互等待的永久阻塞状态，必须同时满足互斥、不可剥夺、请求并保持、循环等待四个必要条件。**
死锁四必要条件：1) 互斥；2) 不可剥夺；3) 请求并保持；4) 循环等待 $\{P_1, \dots, P_n\}$ 形成环。

> [!tip] 考试怎么用
> 注意区分饥饿（单进程、可能就绪态）与死锁（多进程、必阻塞态）；资源分配图有环仅当每类资源仅一个实例时才是死锁充要条件。

### 考点2：死锁预防策略
**通过设置严格限制破坏死锁四个必要条件之一，包括破坏互斥（难实现）、不可剥夺（代价高）、请求并保持（静态分配）、循环等待（有序分配）。**
破坏循环等待：资源编号，进程按编号递增顺序请求，$P_i$ 持有大编号资源时不可申请小编号资源。

> [!tip] 考试怎么用
> 静态资源分配易导致资源浪费和饥饿；资源有序分配法增加了编程复杂性且不利于新增设备。

### 考点3：系统安全状态
**安全状态指存在一个安全序列，使每个进程都能获得所需资源并完成；系统处于安全状态一定不会死锁，不安全状态可能死锁但非必然。**
安全序列定义：存在序列 $\{P_1, \dots, P_n\}$，对每个 $P_i$，其前序进程释放资源后，可用资源满足 $P_i$ 的 $Need$。

> [!tip] 考试怎么用
> 死锁发生时系统必处于不安全状态，但不安全状态不一定演变为死锁（取决于后续请求）。

### 考点4：银行家算法数据结构
**银行家算法需维护 Available、Max、Allocation、Need 四个数据结构，核心关系式为 $Need[i,j] = Max[i,j] - Allocation[i,j]$。**
矩阵关系：$Need[i,j] = Max[i,j] - Allocation[i,j]$；请求向量 $Request_i[j]$ 表示进程 $P_i$ 请求 $j$ 类资源数。

> [!tip] 考试怎么用
> 解题第一步通常是根据 Max 和 Allocation 计算 Need 矩阵；进程最大需求声明后不得更改。

### 考点5：银行家算法执行步骤
**进程请求资源时，系统依次进行合法性检查、可用性检查、试探性分配、安全性检查，仅当安全时才正式分配。**
试探性分配更新：$Available -= Request$，$Allocation += Request$，$Need -= Request$；若不安全则撤销恢复。

> [!tip] 考试怎么用
> 安全性检查是核心，若试探分配后找不到安全序列，必须撤销分配并让进程等待。

### 考点6：安全性算法流程
**安全性算法通过构造安全序列判断状态：初始化 Work=Available，反复寻找 $Need_i \le Work$ 的进程，模拟其完成并释放资源。**
循环条件：找 $Finish[i]=false$ 且 $Need[i] \le Work$ 的 $P_i$；执行 $Work = Work + Allocation[i]$，$Finish[i]=true$。

> [!tip] 考试怎么用
> 若所有进程 Finish 均为 true 则安全；若找不到满足条件的进程且仍有未完成进程，则不安全。

### 考点7：死锁检测与解除
**死锁检测利用资源分配图简化法，死锁定理指出系统死锁当且仅当图不可完全简化；解除方法包括资源剥夺、撤销进程、进程回退。**
死锁定理：系统死锁 $\iff$ 资源分配图不可完全简化（无法删除所有边）。

> [!tip] 考试怎么用
> 检测无须预知未来需求；解除时撤销进程需考虑代价，资源剥夺需防饥饿。

## 易混与对比
**死锁预防 vs 死锁避免**

|特性|死锁预防|死锁避免|
|---|---|---|
|策略|破坏四必要条件之一|动态判断分配后是否安全|
|限制条件|严格，宁可资源闲置|宽松，允许动态申请|
|实现难度|简单，无须运行时检测|复杂，需预知最大需求|
|资源利用率|低|较高|
|典型方法|静态分配、有序分配|银行家算法|

**死锁 vs 饥饿**

|维度|死锁|饥饿|
|---|---|---|
|涉及进程数|两个或更多，形成循环等待|可仅影响单个进程|
|进程状态|必定处于阻塞态|可处于就绪态或阻塞态|
|产生原因|竞争不可剥夺资源且互不相让|资源分配策略不公平（如 SPF）|
|系统状态|相关进程永久无法推进|系统可能正常运行，仅个别被忽略|

**安全状态 vs 不安全状态**

|状态类型|是否死锁|演化趋势|判定依据|
|---|---|---|---|
|安全状态|一定不会死锁|可保证所有进程完成|存在至少一个安全序列|
|不安全状态|可能死锁（非必然）|若进程请求不当则死锁|找不到任何安全序列|
|死锁状态|已经死锁|需外部干预解除|资源分配图不可简化|

**资源分配图有环的含义**

|资源实例情况|图中有环的含义|结论|
|---|---|---|
|每类资源仅一个实例|环是死锁的充要条件|有环必死锁|
|某类资源有多个实例|环仅是死锁的必要条件|有环未必死锁，需简化图判断|

## 闪卡
#card
- 死锁定义的四个必要条件缺一不可吗？::是，只要任一条件不成立，死锁就不可能发生。
- 资源分配图中存在环是否一定死锁？::否，仅当每类资源均仅有一个实例时，环才是死锁充要条件。
- 饥饿与死锁在进程状态上有何区别？::饥饿进程可处于就绪态或阻塞态；死锁进程必定处于阻塞态。
- 可剥夺资源（如 CPU）竞争会导致死锁吗？::一般不会，因为操作系统可强制回收可剥夺资源。
- 破坏互斥条件在实践中可行吗？::不可行，许多临界资源（如打印机）本质不支持并发访问。
- 静态资源分配法如何破坏请求并保持条件？::进程运行前一次性申请全部资源，运行期间不再提出新请求。
- 资源有序分配法如何防止循环等待？::规定进程必须按资源编号递增顺序请求，确保无法形成环。
- 破坏不可剥夺条件的代价是什么？::强制释放可能导致工作失效、设备状态混乱，增加系统开销。
- 系统处于安全状态时会发生死锁吗？::不会，安全状态保证所有进程都能顺利完成。
- 系统处于不安全状态是否一定死锁？::不一定，不安全状态只是可能死锁，取决于进程后续行为。
- 安全序列是否唯一？::不唯一，可能存在多个满足条件的进程执行序列。
- 死锁状态属于安全状态还是不安全状态？::属于不安全状态，死锁是不安全状态的极端情况。
- Need 矩阵如何计算？::$Need[i,j] = Max[i,j] - Allocation[i,j]$，即最大需求减已分配量。
- Available 向量表示什么？::表示系统当前各类资源的可用实例数量。
- 银行家算法对进程最大需求有何要求？::进程运行前需声明最大需求，且整个生命周期内不得更改。
- Request 向量超过 Need 向量意味着什么？::非法请求，因为申请量超过了预先声明的最大需求。
- 银行家算法第一步检查什么？::合法性检查：$Request_i \le Need_i$，确保未超过最大需求。
- 若 Request > Available 系统如何处理？::资源不足，进程必须等待，不进行试探性分配。
- 试探性分配后若系统不安全怎么办？::撤销分配，恢复数据结构原值，让进程等待。
- 正式分配资源的先决条件是什么？::试探性分配后，系统仍能通过安全性算法找到安全序列。
- 安全性算法中 Work 向量初始值是什么？::初始时 $Work = Available$，表示当前可用资源。
- 进程 $P_i$ 被加入安全序列的条件？::$Finish[i]=false$ 且 $Need[i] \le Work$（各分量均不超过）。
- 进程模拟完成后 Work 如何更新？::$Work = Work + Allocation[i]$，即加上该进程释放的全部资源。
- 如何判断系统最终处于安全状态？::所有进程的 $Finish[i]$ 均为 true，即所有进程都能完成。
- 死锁定理的核心内容是什么？::系统处于死锁状态当且仅当其资源分配图不可完全简化。
- 资源分配图简化时如何判断进程可执行？::进程所有资源请求均可被当前空闲资源（总数减已分配）满足。
- 资源剥夺法解除死锁需注意什么？::需防止被挂起进程因长期得不到资源而陷入饥饿。
- 撤销进程法的主要缺点是什么？::代价高，进程已完成的工作丢失，需从头执行。
